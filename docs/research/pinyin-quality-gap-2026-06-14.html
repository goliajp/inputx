诚实的判断

inputx 当前拼音不是"差一点点",而是差一整代工业级 IME 应有的底盘能力。

具体来说有三件根本性的事:第一,没有真正意义上的语言模型(只有 unigram 频率 + 一个二阶 bigram support 的二元判定),没有真正的 trigram 概率 + 平滑;第二,没有联合切分 + 解码的 lattice,长句拼音woshibeijingren不能整句出"我是北京人";第三,大量已经实现的零件(联想、模糊、简拼、Viterbi 组合)当前全部被 gate 关闭,处于"等用户逐个 polish 才能打开"的极小化调试状态。

底盘缺,所以再多 polish 都在搬砖;上层关,所以已有的工程能力都没在为用户产生价值。

但有好消息:词库、评分公式、L0 用户学习、Viterbi 框架、模糊表 —— 这些都已经存在,代码质量也不差。差距更多是"系统性的缺一块 + 选择性的关掉一块",不是"全部从零做"。

balance · 我们已经领先的设计

金身 · 别为追主流破了。

§00 讲"差一代",这一节讲"哪些设计已领先 / 不能动"。读差距报告时别把这俩搞混 —— 差距是单引擎排序能力 vs 主流;金身是多引擎共存的解耦机制 vs 主流根本没做。

已经领先的三件事

1. 三引擎共存的正交矩阵 · 10-tier × {wubi, pinyin, nihongo} 的格子,严格 lexicographic sort。这是 inputx 解耦三种输入方式的唯一方法 —— 主流单引擎 IME 根本不需要,也根本没做。

2. wx > px > nx 五笔优先 · 由 engine_gap_q4 = 110 > within_tier_max_q4 = 100 物理保证,任何 within-tier 分数都翻不过 engine 偏序。Wubi 一级简码 floor = 1,000,000,是 Inputx 五笔的品牌技术承诺(肌肉记忆不被高频拼音夺走)。搜狗不做"五笔优先"—— 你要五笔得装独立软件。

3. 公式驱动 + 数据通道严控 · 排序逻辑里不存在 per-entry hardcoded list / if-branch。系统性问题改公式(z-score 分布 / tier 阈值),per-case 才进六张约定 TSV。这是 inputx 不变成"补丁堆"的关键自律。

我们现在长什么样。

基于代码事实(不是印象)的现状报告。每段都对应到具体文件、函数和路径名,可追溯、可验证。

1.1 全链路:从一次按键到候选浮现

用户按下一个字母 → CompositeEngine::handle_letter() (core/crates/inputx-core/src/composite/engine.rs) → 并行分发到 WubiEngine + PinyinAdapter + 可选的 JapaneseAdapter → 各引擎独立产生候选 → dispatch() (composite/dispatch.rs:64) 执行跨引擎合并规则 → merge() (composite/merge.rs) 统一排序 → 返回给 UI。

拼音侧的核心是 PinyinAdapter,包装了 inputx-pinyin 库,维护输入 buffer 和候选缓存。每次 handle_letter() 触发 refresh_candidates() (pinyin_adapter.rs:1184),它按一个固定顺序执行 七条路径(Path 0a → 3b),把每条路径产生的候选拼起来,再走合并。

这是一个"多路径并联 + 后置融合排序"的形态,而不是经典 IME 教科书里的"统一 lattice + Viterbi 一次解码"。这个差异在 §04.3 会展开。

关键观察 "多路径并联"的好处是模块化、易调试;代价是每条路径的得分要靠手工 scale 才能比较,容易出现某一路径"压制"另一路径的失衡。这恰好是 polish 工作的主要内容。

1.2 评分模型:三轴 log-space 加法

核心评分公式(见 docs/SCORING.md §2 与 composite/merge.rs),v1.4.2 起进入三轴 log-space 加法:

score_q4(c) = log_prior_q4(c) // Q4 定点 (×16) 的 log 频率, 语料先验 + log_likelihood_q4(c) // Q4 定点 的 log 似然: Exact / Prefix / Fuzzy 分级 // Bayesian 解读: P(W|i) ∝ P(i|W) · P(W) // = likelihood · prior → 加在 log 空间 tier(c) ∈ {0..9} // 低 tier 候选无条件压住高 tier (无视频率) // Wubi 简码 = tier 0 floor 1e6 → 保证五笔品牌 // Pinyin 短 phrase = tier 4 (default) L0 promote: pin/freq override 由 user pick 驱动, 3 次相同 (pinyin, word) 自动 pin // PROMOTE_THRESHOLD=3 (ranking.rs:28)

这套打分本身是干净的;问题不在"算得对不对",而在能拿来算的特征太少 —— 没有 bigram 概率(只有 binary support)、没有 trigram、没有 char-level fallback。所以排序失误一旦发生,你能调整的旋钮就只有"加 polish、动 freq",久而久之就变成一份手工词频表。

1.3 词库:量与源

规模。library.tsv 416,598 行;编译后的 pinyin.dict(FST)3.9 MB;另有 1.7 KB 的 bootstrap-only 引导 dict。FST 的 key 编排为 {pinyin}\x00{word},value 是 u64 频率分。

来源(SCORING.md §1.1)。Wikipedia zh / ja(unigram + bigram baseline)、jieba(分词)、Leipzig zh corpus、LCCC-base(口语 / 微博)、Unihan(读音 + 异字)、KANJIDIC2(日文)、OpenCC(繁简映射)、用户 polish 上报(opt-in)、LLM 标注(ambiguous codes)。

处理 pipeline(SCORING.md §1.2)。tools/scoring/ 下 8 步:fetch → extract → normalize(log-rank 跨源)→ layer_assign → merge → llm_annotate(Claude API 批处理)→ validate(QA 门)→ pack(.dict)。每步 resumable + cacheable。

QA 门。回归 70+ baseline 100% 通过;稳定预算 ≥ 95% polish wins 不翻转;覆盖容差 -1% max;LLM judge 采样 200 条均值 ≥ 2.3。

个性化 L0。pins: HashMap<String, String> + pick_counts: HashMap<(String,String), u32> 两张表,3 次 pick 自动 promote。export/import L0Snapshot 由宿主序列化。

结构性缺口。词频固定在 build-time FST 二级结构内,runtime 无法对单条 entry 改 freq;只能靠 L0 层 override,不能让"上周才出现的热词"在不重建 FST 的前提下提升。

02
Benchmark · 主流拼音的关键能力

他们做到了什么。

不是"用了 NLP"的废话总结;是具体算法、具体论文、具体能跑的开源对照。

2.1 语言模型:trigram + 平滑(本地标准答案)

主流本地路线一致是 trigram + Kneser–Ney / Witten–Bell / Backoff 平滑。微软 IME 的 Gao et al. 2002 (ACM TALIP) 是公认起点:trigram + 从 web 自动抓语料 + 最大似然分词训练。开源代表 SunPinyin 明确写 "backoff bigram and trigram language model";训练语料是新浪 / 人民日报数百 MB ~ GB 级。

2015 年起学术界把 NN 引入(Y15-1052),做法是把 NN 的概率"压回 backoff n-gram"喂给 IME —— 保持本地实时性,不上 GPU。再后来 PinyinGPT (ACL 2022) 把 GPT 微调用于 P2C。

商业 IME 的工程结论一致:本地 n-gram(快、小),云端可走 NN/LLM。

对我们的意味 "trigram + 平滑"在 inputx 现状里完全没有 —— 我们只有 unigram + 二阶 bigram 的 binary support 判定(bigrams.ngm 表 MAX 是否 > 0)。这是从"频率表"过渡到"语言模型"之前的最后一站。

2.2 整句解码:Viterbi + Beam(教科书答案)

Chen & Lee 2000 (ACL) 把 HMM + Viterbi 定为 baseline:trigram + 统计分词 + Viterbi。现代实现普遍是 Viterbi + beam search(beam 宽度 16~64)。神经路线把它换成 seq2seq + attention(Moon IME, arXiv:1811.04352);Joint Graph Model(ACL 2014 P14-1142)进一步把 typo 也塞进同一张 lattice。

关键工程结论:不要把"拼音切分"和"汉字解码"分两阶段。把所有合法切分(包括 typo 修正后的)塞进同一张 lattice,让 Viterbi 一起选 —— xianjin → 现金/先进靠的就是上下文 trigram 压倒切分歧义。

2.3 词典与切分歧义

词典量级。主流 IME 核心词库 10~30 万词,核心高频 5~10 万;搜狗细胞词库另有约 3 万领域词库、累计 5000 万词条(2015 数据)。inputx 的 416k 词条规模上不输,但缺少分领域的"细胞"机制。

组织。普遍 trie / DAWG / FST 做前缀检索 + 一张 bigram/trigram 哈希做概率。libpinyin 的 model.bin 就是 zhuyin→word 映射 + n-gram。inputx 的 FST 是同一形态,但"n-gram 那张表"还没成型(只有 bigram support 的 binary 表)。

2.4 模糊音 / 容错 / typo

模糊音独立于 LM,典型是单独的 fuzzy-table(librime spelling algebra 是范本):zh↔z / ch↔c / sh↔s / n↔l / h↔f / r↔l / in↔ing / en↔eng / an↔ang。实现是在输入阶段把每个音节展开成等价集合,可带概率(如 p(zhong|zong)=0.15)。

键盘临近键纠错走 edit-distance ≤ 1 + 键盘邻接图(qw / as 等)。KNPTC (arXiv:1805.00741) 用 NMT 做 typo correction,但工业实现仍是规则 + edit-distance + Viterbi 联合。

2.5 个性化:三件套

动态词频。每次上屏 +1,带指数衰减避免老词卡死。"动态频率"是默认 on 的开关,搜狗等都可关闭(让你看到的排序更可预测)。

自造词收录。连续 2~3 次上屏同一组合 → 自动入个人词库。inputx 的 L0 PROMOTE_THRESHOLD=3 就是同一思路。

多端同步。云端账户同步个人词库 + 用户 n-gram。SunPinyin 把 user n-gram 和系统 n-gram 做线性插值(λ·user + (1-λ)·system),λ 动态。

2.6 联想 · 云输入 · 评测

联想本质就是 trigram LM 的子集 —— 给定 w_{i-2}, w_{i-1} 找 argmax P(w_i | ·),共用同一份 LM 即可。神经路线见 Moon IME、AttnInput。

云输入把同一句拼音同时发到云端,云端用更大 LM + 实时语料(热搜、人名、地名)算 top-1,150~500ms 回插。是搜狗 / 百度的差异化来源。注意安全代价(2024 Citizen Lab 报告明文传输 keystroke)。

评测事实标准两个:MIU Accuracy(Maximum Input Unit 句内最长连续汉字段,top-1/5/10 命中率)+ KySS(KeyStroke Score 按键经济性)。测试集 People's Daily(新闻易)+ chat(口语难)。Top-1 MIU 在 People's Daily 上 SOTA 神经模型 70%+,trigram baseline 在 50% 一线。

最小可走通的主流 MVP 五件套:trigram + Viterbi + 10 万词 trie + 模糊音表 + 用户词频衰减。—— 综合自 SunPinyin / libpinyin / Chen & Lee 2000

这些差距,具体是什么。

01
整句拼音输入
structural missing

症状

用户敲 woshibeijingren 想出"我是北京人",我们出不出来。Path 0b 虽然在 buffer ≥ 8 字节时会跑 Viterbi,但它走的是"先 DP 切分 → 各段独立查 → 拼起来"的形态,而不是把所有候选词作为 lattice 的边一次解码。短 buffer(4~6 字)更是干脆不走 Viterbi。

典型 case:nihaomawojiao(你好吗我叫)、nibuyaozhe(你不要这)在我们这里都不会自然组合。

根因 / 修法

根因是 §1.1 描述的"多路径并联 + 后置融合"形态本身 —— 没有一个统一的解码器把所有候选放到同一张图里争。

修法分两步:
(1)把现有 best_composition_chain() 扩为无约束多词重新分割,不限 buffer 长度;
(2)把分割路径里的"相邻 token bigram 概率"从现在的 binary support 升级为真正的 log-prob(下一条)。

这就是 PLAN-syllable-aware-pinyin.md §4 里被推迟的 Option C。

02
真正的二阶 / 三阶语言模型
structural missing

症状

用户敲 xianjin,我们出"先进"还是"现金"取决于单独看哪个词的 freq 更高。但人写"现金交易"和"先进经验"是不同语境;trigram LM 能利用左右 token 算条件概率,unigram 不能。

所有"为什么这个词排错位"的 polish 工单,根本上都在补这一课 —— 因为我们没有 LM,只能靠手工调 freq。

根因 / 修法

根因:bigrams.ngm 和 bigrams_inter.ngm 只存"有没有共现",不存"共现的对数概率"。

修法分三步:
(1)在 tools/scoring/ 的 pipeline 里加 bigram_lm.tsv,存归一化后的 log P(w_i | w_{i-1}),带 Kneser–Ney 平滑;
(2)新 FST 单独编译,运行时 mmap;
(3)Viterbi 评分项里加 λ · log P(w_i | w_{i-1}),λ 起始 ~0.5,baseline 上调。

评测先用 People's Daily 拼音回译子集,跑通 top-1 MIU。

03
联合 lattice(切分 + 模糊 + typo 同图)
structural missing

症状

同一句话里如果既需要切分歧义判定(xianjin),又需要模糊音(shichuan→四川),又需要 typo 容错(woshibijing 漏 n)—— 我们的多路径形态会让这三种能力互相争抢同一个候选位,且各路径的得分没有可比的概率语义,只能靠手工调常数。

根因 / 修法

根因:七路径每条都在独立产生候选 + 各自打分,然后才合并;模糊与 typo 在打分上加 discount(× 0.3),无法跟其他路径的得分做真正"P(W|i) ∝ P(i|W)·P(W)"的对账。

修法是把这些路径转成同一个 lattice 的不同边:模糊边带 log p(fuzzy_pinyin | true_pinyin)、typo 边带 log p(typo | true)、abbrev 边带常数 penalty。Viterbi 一次出 top-K。

这是上一条 LM 的自然延伸 —— 一旦有了真概率,把多路径融合成 lattice 几乎是自动的。

04
联想 / 模糊 / 简拼 / Viterbi 组合
gated gated

症状

用户体验到的"拼音功能很基础" —— 实际上是因为四大 gate 全开着 true。代码完整,功能存在,但用户看不到。这是"工程已做、体验未交付"的典型断层。

根因 / 修法

根因:2026-06-06 起的 minimal-debug 模式,等用户逐个 polish 才允许打开(见 docs/pinyin-pipeline-gates.md 和 memory pinyin_minimal_debug_state.md)。本身是好做法 —— 不让噪声污染调试信号。

修法不是技术,是流程节奏:每周开一个 gate,2~3 周内全部回归启用,期间用 polish-log + baseline 双向校验。打开一个 gate = 一组 baseline 测试自动 revive,不需要新写测试。

05
用户 n-gram 学习
structural missing

症状

L0 学到的是"用户在 buffer=X 偏好 word=Y";学不到"用户写过 北京 → 大学 的 bigram"。所以用户的语言习惯只能在整词被选中时表达,不能影响同一句子里下一词的概率。

根因 / 修法

根因:L0 表 schema 是 (pinyin, word) → freq/pin,没有 (prev_word, word) → count 这张表。

修法:加 user_bigram: HashMap<(String, String), u32>,每次 commit 链上 +1。LM 评分时用线性插值:P̂ = (1-λ)·P_system + λ·P_user,λ 起始 0.2,随 user data 累积上调到 0.4。SunPinyin 是参考实现。

持久化和 L0 snapshot 同一通道,宿主决定 serde。

06
运行时词频自适应
structural missing

症状

"昨天才出现的人名 / 热搜"我们无法 surface,除非重打 dict 包并发版。

根因 / 修法

根因:freq 固定在 FST 二级 value 里。修法两条路:
(1)side-loadable override:一张可热加载的 TSV/JSON,运行时 merge 到查询结果之上,作为"频率补丁"通道;
(2)远端 deliverable(月度 / 季度 dict drop)+ 校验和签名。

不必走云输入(隐私代价高),但需要一个"轻补丁"通道。

07
行业可比的评测脚手架
structural missing

症状

"我们离搜狗多远"这个问题无法量化回答。现有的 70+ baseline 是回归测试,不是质量基准;LLM judge 200 条采样信号弱;两者都不能对外引用。

根因 / 修法

修法:实现 MIU + KySS 评测脚手架:
(1)挑选评测语料 —— People's Daily 子集 + 一份开源 chat corpus(LCCC 抽样即可);
(2)拼音回译(汉字→拼音,可用 pypinyin)生成 input;
(3)灌入 engine,取 top-1/5/10,匹配原句计算 MIU accuracy;
(4)同样语料跑一份 SunPinyin / libpinyin 作对照线。

有这个数字才能跟"主流"对话,而不是凭印象。

05
Roadmap · 改进路径(三阶段)

从这里去那里。

不画一张"理想终态架构图"。给一条可走、可中断、可回退的三阶段路径,每阶段的产出独立有价值。

底盘清理

est. ~ 4 weeks · 不动数据 · 只翻 gate / 加评测
  1. 逐周翻 gate。每周打开一个 gate(顺序建议:FUZZY → ASSOCIATION → COMPOSE → PREDICTION),让 baseline 自动 revive,用 polish-log 校验。完成后用户体验立刻接近"已有工程能力的全量"。
  2. MIU 评测脚手架。tools/eval/ 新建,People's Daily 子集 + LCCC 抽样;拼音回译用 pypinyin;实现 top-1/5/10 MIU accuracy + KySS。同步跑 SunPinyin / libpinyin 对照线。
  3. side-loadable freq override。一张可热加载的 polish-overlay 表,把"昨天才需要 polish 的词"从重建 dict 解耦。

底盘升级

est. ~ 8 weeks · 加 LM / 改解码器
  1. 真 bigram LM。在 tools/scoring/ 加 09_bigram_lm,产 bigram_lm.dict(Kneser–Ney 平滑后的 log-prob FST)。运行时 mmap。
  2. Viterbi 全长统一。打通无约束长句重切分(Option C),把 Path 0b 的 ≥ 8 字节阈值降到全 buffer。短 buffer 走简化版 lattice,长 buffer 走 beam search。
  3. 联合 lattice。模糊 / typo / abbrev 转为 lattice 边,带 log-prob;打分项统一为 prior + likelihood + LM。
  4. 用户 bigram。L0 加 user_bigram 表,LM 评分线性插值。

顶盖打磨

est. ~ ongoing · 朝行业水平细节
  1. Trigram。当 bigram 上线稳定后,加 trigram(更大语料 + 更多内存代价)。MIU 跑分应能从 50% baseline 攀到 60%+。
  2. 细胞词库。schema 设计 + 一两个示范包(IT / 金融),先用 polish 上报数据自孵化。
  3. 键盘临近键 typo。在 lattice 内加 typo 边(edit-distance ≤ 1,带 keyboard adjacency penalty)。
  4. 长简拼。zhrmghg → 中华人民共和国;在 lattice 加 abbrev 边,penalty 由频度调。
  5. (可选)神经 rerank。本地 trigram 出 top-K,小型 NN 模型(< 50 MB)rerank top-N;可选,不强求。
· · ·

关键取舍

云输入暂不做。隐私代价高(2024 Citizen Lab 报告披露搜狗等明文传输 keystroke),且 inputx 的项目定位偏"本地、可信、可审计"。我们不靠云,但要把本地能做的做到位 —— 这才是差异化。

不上 GPU、不要求联网。Phase 02 的 LM 仍是 n-gram,本地 FST,无 runtime 神经依赖。Phase 03 的神经 rerank 是可选项,且要严格控模型体积(< 50 MB)与延迟(< 10ms)。

polish 流程不变。Phase 01-03 的所有改动都在保留逐字 polish 工作流的前提下做。LM 不是替代 polish,是给 polish 一个更高质量的起点。

风险预警 Phase 02 的 LM 上线是一次"语义层换装",不可避免会引发现有 polish 表的部分翻转。建议在切换前后跑双轨 baseline,保留旧打分作 fallback 一段时间。这是和 polish 用户的契约问题,要提前沟通。

06.7 · 两份实操配方(可立刻动手)

配方一 · 立刻搭 MIU 评测脚手架

需要 3 份数据:

① 黄金 hanzi corpus(句级) — 抓 People's Daily online 近一年 或用 brightmart/nlp_chinese_corpus 的 news2016zh;jieba/THULAC 切句 → 按 MIU 定义(非汉字分隔的最长汉字串)再切 → 目标 ~5 万 MIU,做 dev/test split。

② 平行 pinyin 序列 — pypinyin.lazy_pinyin(miu, Style.NORMAL) 一过;多音字策略:train/dev 用 default;test 单独人审 1000 条做高质量 MIU —— 否则 metric 会把 pypinyin 选错的多音字算成 IME 的错。

③ typo 噪声集(可选) — 用 RIME fuzzy_pinyin 按 1%-5% 注 noise;SIGHAN-2015 confusion-set 倒推到 pinyin level。

第一个 metric:Top-K MIU accuracy(Top-1 / 5 / 10)。Top-1 ≈ "用户不翻页能否打出来"。第二步加 KSR 才能跟 KySS 系对齐。

配方二 · 训像样 trigram LM

底盘三档:

· 最小 · Wikipedia + LCCC-base + THUCNews ≈ 5 GB · 1-2 天验证 pipeline

· 中等推荐 · 上 + CC-100 zh ≈ 70 GB · 第一版可用 trigram

· 大 · 上 + SkyPile-150B 子采样 + MNBVC 聊天/小说子集 ≈ 200 GB · 接近搜狗级

清洗 pipeline 顺序(顺序很重要): wikiextractor → 去 boilerplate → fasttext lid (0.7 阈值) → OpenCC t2s.json → 按 。!?… 切句 → 句长 4-120 字 + 汉字占比 ≥0.6 过滤 → MinHash 句级去重 → jieba.cut(HMM=False) + 自定义词典 → KenLM lmplz -o 3 + modified Kneser-Ney → .arpa → .binary → IME 端 mmap。

license 安全配方(避开灰色):用 Wikipedia + CC-100 + LCCC + SkyPile;避开 THUCNews/PFR 1998/WuDao。
