三引擎在矩阵中"正交" —— 各自有自己的 tier 分布公式,不互相干扰。

为什么这条不可动

主流单引擎 IME(搜狗 / libpinyin)根本没有这个问题 —— 它只有一种输入路径,排序就是单一维度。inputx 是三引擎共存,如果允许跨引擎调参,任何一处变动同时影响三方关系 —— 复杂度爆成 n²。

正交矩阵的意义就在于:把 n² 解成 n + n + n。pinyin 排序问题只调 pinyin 的 tier 分布(tier_quantile_pinyin μ/σ + 各 tier z 阈值);wubi 只调 tier_wubi 的 freq floor;nihongo 只调 nihongo z-score 分布。

主流为什么不需要

libpinyin / SunPinyin / Mozc 都是单引擎:输入 = pinyin / 注音 / kana 之一,候选生成 = 单一路径,排序 = 单维。它们没有"三种输入方式同时出现"的问题。

这套正交机制是 inputx 独有的架构资产 —— 主流抄不来,因为它们不需要;但我们抄主流任何东西的时候,必须先证明新东西不破这个矩阵。

跟律二的关系 本律建立"格子",律二建立"格子间的 wx > px > nx 偏序"。两律合起来才是完整正交矩阵。

律 · 二

wx > px > nx · 五笔雷打不动优先

同 tier 内,五笔永远压住拼音,拼音永远压住日语 —— 由 engine_gap_q4 = 110 物理保证(大于 within_tier_max_q4 = 100)。

"inputx 五笔" 的品牌承诺

"inputx 五笔优先"不在 per-entry 代码里,而在 engine offset 这一个常数里。任何候选属于 wubi 引擎,只要进了 tier N,就自动在该 tier 内压住 pinyin / nihongo。

Wubi 一级简码 floor = 1,000,000(core/crates/inputx-wubi/src/layer.rs:47-54),对应 tier 1 顶部。这是 Inputx 五笔的技术承诺 —— 你的肌肉记忆不会被任何 pinyin 高频词夺走。

多级编码的冗余保护

用户 2026-06-07 洞察:五笔有多级编码(简码 cu / 更长 cua / 全码 cuah)本身就是冗余路径。简码层按字频退一点点是安全的 —— 因为全码层始终精确 #0。

实测案例:cu → 骈 #5(让位给 粗 / 促),但 cua → 骈 #0 且 cuah → 骈 #0。五笔用户真要生僻字,多打 1-2 码即 #0,零损失。

历史教训 · 2026-06-07 engine_gap=40 探测 我曾尝试调 engine_gap_q4 从 110 → 40。结果:日语越过拼音 + 常用五笔被高频拼音夺 #0,完全失控。动这一个常数同时影响三引擎关系,这就是律二禁止跨引擎调参的实证。30 分钟后 revert,作为本律永久案例。
历史教训 · 2026-06-03 跨引擎 sweep 我曾按"pinyin freq=0"把 wubi 简码批量降到 tier 5。违背 wx > px,误伤 39 个高频五笔字(碰 / 虎 / 拉 / 谍 / 东…),后来全部 revert。从此立约:禁止跨引擎 per-(buffer, word) 批量 sweep。
对照主流 · 搜狗有没有这个 搜狗没有"五笔优先"这种东西 —— 它就是单一拼音引擎。你要五笔得装独立软件。inputx 把"切换无感的多引擎共存 + 五笔肌肉记忆受保护"做成核心价值,这是主流根本不做的差异化。学搜狗的 LM 是为了拼音侧更强,不是为了让五笔让位给拼音。

律 · 叁

Tier 0 神圣 · 仅留 user assertion

Tier 0 是绝对顶,只为用户的显式 pin 和结构性 top 保留。任何其他想要"顶 #0"的需求,都在 tier 1 + engine offset 里实现。

为什么 tier 0 不能随便填

如果系统默认就把"我认为应该在顶"的词放 tier 0,那么用户的显式偏好就没有专属表达空间 —— 因为 tier 0 已经被算法占用了。

留 tier 0 给 user assertion,意味着:用户 pin 一个词,它无条件压住任何其他候选。这是用户控制权的最后一层保障。

结构性 top 走 tier 1

"wubi 简码应该在顶" —— 这是结构性 top,走 tier 1 + engine offset(因为 wubi engine offset 已让 tier 1 wubi 永远压住 tier 1 pinyin)。

"jukugo 应该在顶" —— 不,jukugo 走 tier 2 phrase。如果它真的高频,会在 within-tier 内自然胜出。

禁特殊列表 · Rust 里没有 per-entry 硬编码

任何形如 const FOO: &[(&str, &str)] = &[...] 或 if (buffer, word) == ("yi", "就") { ... } 的 per-entry carveout 永久禁止。

const BAKED_EXCLUSIONS: &[(&str, &str)] = &[(...), (...)]; ✗ const PRIOR_CORRECTIONS: &[(&str, i32)] = &[(...), (...)]; ✗ if (buffer, word) == ("yi", "就") { score *= 1000.0; } ✗ let protect_list = &["就", "民", "长", ...]; ✗ fn is_protected(buf: &str, w: &str) -> bool { matches!(... ) } ✗
match layer { Jianma2 => 1, Auto => 4, ... } ✓ // layer→tier 是结构性 if pinyin_dict.char_max_freq(c) >= 20_000 { tier 1 } else { ... } ✓ // 频率阈值统一应用 'z' carve-out for wubi standalone ✓ // 五笔 86 语言性质 l/n + ü pinyin morphology aliasing ✓ // 拼音拼写规则

"特殊"的判定线

一份 list 是"特殊"的,当且仅当它编码了 per-(buffer, word) 数据且没有结构性依据。区分线:

  • 结构性 = 编码输入系统本身的性质(拼写、layer 模型、IME 模式),这是框架。允许。
  • 数据 = 因为 polish-log 证据要求才存在的 (buffer, word) / (word, value) tuple。这只能进 tier_overlay.tsv / quickfix_boost.tsv 等 TSV,不能进 Rust 源码。

这条规则永久 · 不打折

本规则不论谁提议都不松:

  • 不论是我(Claude)主动提出
  • 不论用户明确请求
  • 不论"就这一条很无害"的诱惑
  • 不论 deadline 多紧

如果一个 polish 需求矩阵 + 数据面表达不了,结论是 "框架缺一条结构性规则" —— 不是"加一个 carveout"。

关键陷阱 · kongdang method

2026-06-13 发现的 polish 陷阱(daiban 案例):当 Class B 重排集合含一个刚加的 source=polish 行,quickfix_boost MAX overlay 不可靠地驱动顺序 —— probe score 显示 boost 起作用,但 engine 返回的 ORDER 把新 polish 行沉到末尾。

正解 = kongdang method:直接在 library.tsv 设 clean-descending freq + 全部标 source=polish。让 base freq 确定性地驱动 IDF Path-1 snapshot 顺序,单一真理源,不靠 quickfix overlay。

没有第七张表

如果你发现自己想创建第七张 overlay 文件 —— 框架缺一个结构性 knob,修在 engine_weights.toml 或 producer 的 natural-tier 逻辑里,不是在新的 per-entry 表里。

如何区分系统 vs per-case

判断线:同一类问题会不会在其他 buffer / entry 上重现?

修宪程序 · 觉得规则错了怎么办

不会有这种事。但万一确实矩阵 + 数据面表达不了用户需求,程序如下 —— 不准用 per-entry carveout 作 workaround。

修宪 6 步

  1. STOP。先停下,不写代码,不动 TSV。
  2. articulate gap:精确说出"什么结构性规则缺了"。不能是"我需要把这个词排前"。要是"low-freq jukugo 的 tier 1 placement rule 缺少 freq-aware 截断"。
  3. propose framework extension:新 tier-naming rule / 新 producer-side natural-tier 公式 / 新 TOML knob。具体到改哪个文件、加什么常数、怎么计算。
  4. get user sign-off。用户明确点头才能继续。
  5. extend the framework。改公式 / 加 knob。
  6. continue。回到正常 polish 流程。
carveout 永远是错答案。carveout 的代价会复利(下一个类似问题没法靠 carveout,要么再加一个 carveout,要么承认框架缺失);framework gap 修一次永久受益。这是 inputx 不变成"补丁堆"的关键。

这些金身 · 主流为什么没有

主流 IME 都是单引擎 —— 它们不需要解耦"多种输入方式";它们的复杂度天然是 n,不是 n²。所以它们没有正交矩阵、没有 wx > px > nx 这种偏序。

金身条款inputx搜狗 / libpinyin / Mozc对照解释
正交矩阵 (tier × engine) 必需 · 三引擎共存的解耦机制 不需要 · 单引擎 它们只有"一种输入" → 单维度排序 → n 复杂度
wx > px > nx 偏序 必需 · 五笔肌肉记忆保护 不存在 · 五笔得装另一个软件 "切换无感的多引擎共存"是 inputx 独有差异化
禁特殊列表(律四) 永久 · 防补丁堆腐烂 各家不一 libpinyin 偶有 const 列表;Mozc 走数据面更严谨
公式优先(律六) 永久 · 系统性问题改公式 主流靠云端 retrain 解决 我们不靠云,所以本地公式必须更可调
修宪程序(律七) 必需 · 防止 carveout 复利 商业项目不需要这种自律 开源 + 小团队 + 长期维护,自律是唯一保护
不为追主流破金身。学搜狗 LM 是为了让各引擎在自己 tier 内排得更准(within-tier scoring 升级),不是为了把三引擎熔成一个、不是为了拿掉 wx > px > nx、不是为了在 Rust 里加 per-entry carveout 来"压主流一头"。金身先于性能。

违宪自检 · 每次改动 PR 必过

研究报告、爬升执行表中的每一个 CP 完成后,把这 8 个 ☐ 过一遍。不能全过就不能 merge。

PR 自检 · 8 问

  1. 改动是否引入了新的 per-(buffer, word) const list 或 if-branch?
    grep const.*\[(.*,.*)\] + if .* == \(".*",.*"\)。有任何匹配 = 违律四。
  2. 改动是否动了 engine_gap_q4 / within_tier_max_q4?
    grep engine_gap_q4 在 diff 里出现 = 违律二。修宪程序走起。
  3. 改动是否动了 tier 0 的填充规则?
    grep tier.*0 在 producer 代码里赋值 = 违律三。tier 0 只能由用户 pin 写入。
  4. 改动是否创建了新的 overlay TSV 文件?
    git status 含 tools/scoring/data/polish/*.tsv 中不在 §05 六张表的新文件 = 违律五。
  5. 改动是否用 overlay TSV 修了一个 class 级问题?
    检查 polish 报告:同一类问题(低频 X 压高频 Y)在其他 buffer 是否会重现?会 = 系统性 = 改公式,不是 overlay。违律六。
  6. 改动是否跨引擎调参?
    diff 同时改了 tier_quantile_wubi + tier_quantile_pinyin + tier_quantile_nihongo 中两个或以上 = 警示。律一禁跨引擎耦合。
  7. 改动是否破坏 wubi 简码 #0 承诺?
    跑 cargo test session::wubi_simcode_priority。有任何 fixture 不再 #0 = 违律二。回退或修宪。
  8. 改动是否绕过了修宪程序?
    如果改动属于"我觉得规则错了" —— STOP。律七 6 步走完没?用户 sign-off 拿到没?
